## 1. 목적

본 문서는 Stage 01(SRS)에서 AI에게 요청을 작성하는 모든 **Human 사용자**를 위한 프롬프트 작성 기준이다.  
요구사항이 설계/구현 정보로 오염되지 않도록 **형식·언어·제약**을 명확히 안내한다.

---

## 2. 언제 참고해야 하는가

- 신규 요구사항을 정의·정리·확정할 때
- PRD/SRS 문서를 작성하거나 업데이트할 때
- “요구사항 vs 설계” 경계가 모호하다고 느낄 때
- AI에게 비즈니스/도메인 관점만 요청하고 싶을 때

---

## 3. SRS 단계 핵심 원칙

- **What 전용**: 설계·구현 How 판단, 기술 스택 제안 금지
- **비즈니스 언어**: 이해관계자, 운영 시나리오, 목표 지표 중심으로 기술
- **Traceability**: 모든 요구사항에 ID·근거·출처 명시
- **우선순위**: Helios → Contract → Index → Guide 순으로 적용

### 3.1 출력 모드 판별 규칙 (중요)

요청을 작성하기 전에, 먼저 “원하는 결과 유형”을 아래 우선순위로 판별한다.

```
생성 요청 > 출력 요청 > 내용·용어 정리 요청 > 일반 설명
```

- **생성 요청**: `.md` 파일로 “생성”되길 원함(파일 단위 결과)
- **출력 요청**: 복사/저장 가능한 “Artifact” 형태로 출력되길 원함(코드 블록 기반)
- **내용·용어 정리 요청**: 학습/EDU 정리처럼 구조·Footnote 규칙을 강하게 적용
- **일반 설명**: 설명 중심(필요한 부분만 코드/표)

### 3.2 StudyNote(정리/EDU) 출력 규칙 (필수 조건으로 명시 권장)

정리/EDU 문서를 요구하는 경우, Output/Constraints에 아래 조건을 **명시적으로 포함**하는 것을 권장한다.

- 문서 **첫 줄에 `#Tag`** 등록
- Footnote는 **정의 대상 용어 토큰 바로 뒤**에 직접 매핑(문장 끝/괄호 전체 부착 금지)
- Bold 용어 뒤에는 **공백 1칸** 유지(예: `**용어[^1]** 을`)
- 표준은 `🖋️ StudyNote Markdown Rulebook`을 따른다
  - 참고: [🖋️ StudyNote Markdown Rulebook](🖋️%20StudyNote%20Markdown%20Rulebook.md)Rulebook.md)

## 4. 권장 프롬프트 기본 구조 (5요소)

1. **역할(Role)** – 요구사항 분석가 / PO / Business Analyst 등  
2. **작업(Task)** – 정의 / 검증 / 정리 / 분류 등 목적  
3. **맥락(Context)** – 이해관계자, 운영 환경, 목표, 제약  
4. **출력 기대(Output)** – SRS 섹션, 표, 목록, ID 체계 등  
5. **제약(Constraints)** – 설계 금지, 용어 제한, 기준 명시

### 예시
```
당신은 요구사항 분석가입니다.
MES 자재 관리 기능 요구사항을 정리해주세요.
현업 사용자와 운영팀 관점이며 비즈니스 언어만 사용합니다.
SRS 형식으로 기능/비기능 요구사항을 구분하고 ID를 부여해주세요.
설계나 구현 가정은 하지 말아주세요.

출력은 StudyNote 규칙을 따르는 정리 문서로 작성해주세요.
- 문서 첫 줄에 #Tag를 등록해주세요.
- 전문 용어/약어는 최초 등장 시 Footnote로 정의하고, 용어 토큰 바로 뒤에 [^n]을 직접 부착해주세요.
- Bold 용어 뒤에는 공백 1칸을 유지해주세요. (예: **용어[^1]** 을)
- 문서 마지막에 ## Footnotes 섹션을 포함해주세요.
```

## 5. 좋은 SRS 프롬프트 작성 원칙

### 5.1 역할을 요구사항 관점으로 고정
- ✅ 요구사항 분석가 / Product Owner / Business Analyst  
- ❌ 아키텍트 / 개발자 / 엔지니어

### 5.2 범위·대상을 명확히
- 포함: 사용자/운영/비즈니스 요구, 정책, 제약  
- 제외: 기술 스택, DB 구조, 컴포넌트 설계

### 5.3 맥락은 시나리오·목표 중심
- 이해관계자, KPI, 운영 프로세스, 비즈니스 이벤트  
- 클래스/모듈/데이터 구조 표현 금지

### 5.4 출력 형식은 요구사항 구조에 맞춤
- Functional / Non-Functional / Constraints / Assumptions / Open Issues  
- 표 사용 시 ID·설명·근거·상태를 명확히 기재

## 6. 요청 유형별 작성 예시

### 6.1 요구사항 정의
```
당신은 요구사항 분석가입니다.
설비 알람 관리 기능의 요구사항을 정의해주세요.
현업 오퍼레이터 관점이며 기능/비기능 요구사항으로 구분합니다.
설계나 기술적 가정은 하지 말아주세요.

출력은 StudyNote 규칙을 따르며, 첫 줄에 #Tag를 포함하고, 전문 용어/약어는 Footnote로 정의해주세요.
```

### 6.2 요구사항 검증
```
다음 요구사항 목록을 검토해주세요.
중복, 모호함, 누락 여부만 지적하고 개선안을 제안해주세요.
설계 방향 제시는 하지 말아주세요.

출력은 StudyNote 규칙을 따르며, 첫 줄에 #Tag를 포함해주세요.
용어/약어를 언급할 경우, Footnote를 용어 토큰 바로 뒤에 직접 부착해 정의해주세요.
```

### 6.3 문서 정리
```
다음 내용을 SRS 문서 구조로 재정리해주세요.
요구사항 의미는 유지하고 표현만 명확히 해주세요.
Traceability를 위해 항목별 고유 ID를 부여해주세요.

출력은 StudyNote 규칙을 따르는 정리 문서로 작성해주세요.
- 문서 첫 줄 #Tag 포함
- 전문 용어/약어 Footnote 직접 매핑(용어 토큰 바로 뒤)
- Bold 용어 뒤 공백 1칸 유지
- 마지막에 ## Footnotes 포함
```

## 7. 피해야 할 요청 방식

- “어떻게 구현하면 좋을까?”, “아키텍처를 제안해줘”
- DB 구조, 클래스 다이어그램, 코드 수준 상세 요청
- 성능/보안 설계까지 포함한 How 지시
- “대충 정리해줘” 같은 맥락 없는 단문 명령
- SRS에 없는 요구사항을 임의로 추가하도록 지시

---

## 8. AI 내부 규칙과의 관계

- AI는 **Helios** 및 **Contract 문서**를 최우선으로 적용한다
- 본 가이드는 Human 참고용이며 Rule과 충돌 시 항상 Rule이 우선한다
- 프롬프트 작성 후에도 Helios/SRS 위반 요소가 없는지 자체 점검한다

---

## 9. 결론

정확한 요구사항 산출물은 **정확한 질문**에서 시작된다.  
본 가이드를 활용해 요청을 구조화하면 AI는 Helios 체계를 벗어나지 않고,  
SRS 단계에 필요한 결과만 안정적으로 생성한다.
