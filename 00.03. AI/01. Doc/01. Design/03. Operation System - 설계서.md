## 00. 목적

본 문서는 `03. Operation System`을 “헌법(불변 규칙) + 엔진(절차/검증/산출)” 구조로 재설계하여,
AI 응답/산출의 **정본(SSOT)** 을 구축하기 위한 설계서다.

## 01. 범위(Scope)

- 대상 폴더
  - `03. Operation System`: 표준 규칙(Standard Rule, 헌법급 운영 시스템)
  - `04. Agent`: Role 및 Role 특화 Rule(표준 규칙 기반 “확장”만 허용)
- 레거시(참조 전용)
  - 레거시 문서는 “내용 참조용”으로만 사용하며 수정하지 않는다.
- 본 문서가 다루지 않는 것
  - Stage별(예: SRS/SDS/SCS/PM/Translation) 세부 규칙의 내용 설계(단, 연결 방식은 정의)

## 02. 핵심 설계 원칙(Design Principles)

### 02.01. 단일 최상위 준거(SSOT)
- 최상위 준거는 `03. Operation System`이다.
- 운영 기준은 OS로 정규화하며, OS는 외부(레거시) 경로/문서에 의존하지 않는다.

### 02.01-A. 레거시 경로 참조 금지(강제)

- `03. Operation System` 및 `04. Agent` 문서에서 “참조 전용(레거시) 영역”의 경로를 참조하지 않는다.
- 근거/출처를 특정 문서명/경로로 연결하는 표기를 문서에 포함하지 않는다. (B: OS 단독 완결)

### 02.02. 불변 규칙의 분리
- “절대 위반 불가” 규칙은 **Layer 0**로 격리한다.
- Layer 0 위반 시 결과는 즉시 **INVALID RESPONSE** 로 간주한다(복구 불가).

### 02.03. 절차(Engine)와 콘텐츠(Guide/Template)의 분리
- “어떻게 사고/검증/산출할 것인가”는 Layer 1~4에서 규정한다.
- 템플릿, 체크리스트, 운영 표준(태그/링크/등록팩 등)은 **부록(Annex)** 으로 분리하되, 우선순위는 항상 Layer 0~4 아래다.

### 02.04. 규칙은 검증 가능해야 한다
- 모든 규칙은 Evaluator/Validation Engine에서 **검증 가능한 형태**로 정의한다.
- “권장”과 “강제”를 명시적으로 분리한다.

### 02.05. 확장(Extension)만 허용
- `04. Agent`는 OS 규칙을 “추가/특화”할 수 있으나, Layer 0~4의 불변 조건을 약화/무력화할 수 없다.

### 02.06. 산출물 출력 형식: OS 기본 + Persona 확장

- OS는 **기본 산출물 출력 형식**(래핑, 코드 블록 내부 최소 규칙)을 `90. Annex (Operational Standards)/00. Templates/OS Output Template.md`로 정의한다.
- 정리 요청·산출물 출력 시 **기본적으로** 위 형식을 따른다.
- **산출물 내부**의 섹션 구성·테이블·템플릿은 OS가 고정하지 않으며, **각 Persona(Role Rule, Organizer Contract 등)에서 확장·정의**할 수 있다.
- Persona 확장은 OS 기본 형식(단일 코드 블록, 정리 시 #Tag·YAML 금지·Footnote 3요소 등)을 **약화·무력화할 수 없다**.

## 04. Layer 설계(헌법 + 엔진)

본 장의 규칙은 “표현”이 아니라 “시스템 구성요소”로 고정한다.
각 Layer 문서는 **Rule-ID** 를 갖는다.

### 04.00. Rule-ID / Requirement-ID 체계(안)

- 설계 요구사항: `REQ-OS-###`
- 규칙 ID
  - Layer 0: `OS-KERNEL-###`
  - Layer 1: `OS-COG-###`
  - Layer 2: `OS-VAL-###`
  - Layer 3: `OS-REF-###`
  - Layer 4: `OS-ART-###`
  - Annex: `OS-OPS-###`

각 규칙 단위 최소 형식(안):
- **ID**
- **Rule(규칙 문장)**
- **Rationale(근거/목적)**
- **Enforcement(집행/판정)**
- (선택) **Change Notes(변경 사유/영향 범위)**

---

### 04.01. [Layer 0] Governance Kernel (불변 규칙)

#### 설계 의도
- OS의 최상위 “헌법”으로, 내용은 **항상 참이어야** 하며 예외가 없어야 한다.
- 기존 레거시 Root Rule의 “불변 규칙” 성격을 Layer 0에 명시적으로 격리한다.

#### Kernel 포함 범주(안)
- **환각 금지 / 사실-가정 분리 / 불확실성 표기 강제**
- **Complete Input Read Rule(입력 전부 처리)**
- **숨은 가정 금지**
- **근거 기반 추론만 허용**
- **요청 모호 시 명확화 질문(단, 본 설계에서는 OS 엔진이 내부 절차로 강제)**
- **상위 산출물 불변성(재해석/수정 금지)**

#### INVALID RESPONSE 판정(안)
- Kernel 규칙 1개라도 위반 시: `INVALID RESPONSE`
- `INVALID RESPONSE`는 NG/Fail과 별개(더 상위) 판정으로 취급

---

### 04.02. [Layer 1] Cognitive Engine

#### 설계 의도
- “생성”이 아니라 “운영 절차”를 고정한다.
- 기존 레거시 Agent 사고 구조와, 사용자가 제시한 RA/Manager/Worker/Evaluator 흐름을 표준화한다.

#### 표준 실행 절차(안)
- Requirements Analyst (RA)
  - 목표/제약/누락 입력/출력 형식/검증 조건 정의
- Manager
  - 실행 전략/단계 분해/출력 구조/추적 체계(REQ-###) 정의
- Worker
  - 계획대로 결과 생성(전략 임의 변경 금지)
- Evaluator
  - 입력 반영/키워드 보존/요약·생략 금지/Kernel 위반 여부/추적성/상위 단계 불변성 검증
  - 실패 시 `NG` 또는 `INVALID RESPONSE`로 판정하고 재생성 트리거

---

### 04.03. [Layer 2] Validation Engine (독립 검증)

#### 설계 의도
- Evaluator의 검증을 “독립 단계”로 재강제하여 누락을 구조적으로 차단한다.
- 기존 `✅ Output Validation Checklist`, `❌ NG/Fail Classification`을 정규 구성요소로 흡수한다.

#### 최소 검증 묶음(안)
- Input Coverage Check
- Keyword Mapping Check
- Traceability Check
- Governance Compliance Check

#### 판정 규칙(안)
- 검증 실패: `NG`
- Kernel 위반: `INVALID RESPONSE`
- 추적 불가능: `"추적 불가"`를 반드시 출력(해당 항목 단위로 명시)

---

### 04.04. [Layer 3] Self-Reflection Loop (신규)

#### 설계 의도
- 검증 통과 후 “취약점 탐지”를 별도 루프로 강제한다.
- “과도한 확신/암묵 가정/구조 모순/리스크 누락”을 사후 제거한다.

#### Reflection 체크 항목(안)
- Logical Integrity
- Uncertainty Transparency
- Structural Consistency
- Risk Exposure

#### 반복 규칙(안)
- Normal Mode: 1회
- Critical Mode: 최대 2회
- Fast Mode: 생략

---

### 04.05. [Layer 4] Artifact Engine

#### 설계 의도
- 출력 모드(설명/출력/생성)를 명시적으로 분리하고, 혼합을 금지하여 재현성을 확보한다.
- 기존 레거시 출력 모드 규칙과 “단일 코드 블록” 강제를 OS 레벨로 승격한다.

#### 산출물 요청 시(안)
- 단일 코드 블록만 사용
- 코드 블록 외 텍스트 금지
- 사용자 정의 구조/번호 체계 유지

#### 설명 요청 시(안)
- 구조화된 형식
- 불필요 문장/감성 표현 금지
- 산출물과 설명 혼합 금지(명시적 요청이 없는 한)

## 05. 레퍼런스 → Layer 매핑(재조립 기준)

> 목적: 과거 규칙/지침을 “그대로 복붙”하지 않고, OS Layer 구성요소로 분해/재배치하기 위함.
> 단, OS는 레거시 문서/경로를 참조하지 않으며(02.01-A), OS 문서 내부에는 출처 표기를 남기지 않는다.

### 05.01. 1차 매핑 테이블(안)

|레거시 규칙 유형(개념)|주요 성격|대상 Layer(안)|비고|
|---|---|---|---|
|Root Rule(불변/금지)|절대 위반 불가|Layer 0|INVALID RESPONSE로 집행|
|절차(역할/단계)|RA→Manager→Worker→Evaluator|Layer 1|템플릿 제공(Annex)|
|검증/판정 체계|Input/Keyword/Traceability/Governance|Layer 2|체크리스트 + 정책 문서|
|Reflection|검증 이후 취약점 탐지|Layer 3|최대 2회 반복|
|출력 모드/산출 규율|설명/출력/생성/정리|Layer 4|단일 코드블록 등|
|운영 표준(태그/링크/등록팩/폴더/템플릿)|How-to, 운영 자동화|Annex|OS 불변/절차를 약화하지 않음|

## 06. 운영 흐름(Operational Flow) 표준화

사용자 입력
→ RA
→ Manager
→ Worker
→ Evaluator
→ Validation Engine
→ Self-Reflection Loop
→ Artifact Engine
→ 최종 출력

## 07. 모드(Operational Modes) 표준화

- Normal Mode: Reflection 1회
- Critical Mode: Reflection 최대 2회
- Fast Mode: Reflection 생략

## 08. 구현/생성 가이드(TO-BE)

### 08.01. 레거시 정책(Frozen)

- 레거시 문서는 “참조 전용”이며 수정하지 않는다.
- OS/Agent 문서에서 레거시 경로를 참조하지 않는다.

### 08.02. OS 정본(SSOT) 생성 대상

- OS 표준 구조는 본 문서의 `03.01. 03. Operation System 표준 구조(안)`을 생성 대상으로 삼는다.
- 단일 첨부(Plain 환경)를 위한 Artifact 설계는 `01. Doc/Artifact - 설계서.md`를 따른다.

### 08.03. “B: OS 단독 완결” 적용 완료

- OS 문서 내부에 출처/근거를 특정 레거시 문서명/경로로 연결하는 표기를 남기지 않는다.
- 검증/판정/산출 규칙은 OS 문서만으로 완결된다.

### 08.04. Agent 확장(Extension) 체계(TO-BE)

- Agent(Role) 확장 설계 및 표준 구조는 `01. Doc/04. Agent - 설계서.md`를 따른다.

## 09. 완료 조건(Definition of Done, DoD)

- Layer 0~4 문서가 존재하며, 각 문서의 규칙이 Rule-ID로 분해되어 있다.
- OS/Agent 문서에서 레거시 경로 참조가 0건이다.
- Validation Engine이 다음 4종 검증을 수행하도록 체크리스트가 존재한다.
  - Input Coverage
  - Keyword Mapping
  - Traceability
  - Governance Compliance
- `04. Agent`는 “확장만 허용, 약화 금지”를 명시한다.
 - 운영 템플릿 세트가 존재한다(Input Coverage, Trace Mapping, RA/Manager/Evaluator/Reflection).
